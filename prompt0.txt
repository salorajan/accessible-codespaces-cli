1. Project Overview and Architectural Objectives
The goal of this project is to construct a public, fully accessible reference repository (accessible-codespaces-cli) and accompanying instructional curriculum. The tutorial demonstrates how a visually impaired developer using a Windows workstation, a screen reader (NVDA or JAWS), and Windows Terminal can provision, configure, develop inside, and tear down GitHub Codespaces exclusively via the GitHub CLI (gh), completely bypassing the accessibility barriers of browser-based web IDEs.

1.1 Core Deliverables

2. Accessible Devcontainer Spec: A .devcontainer/devcontainer.json configured specifically for headless SSH sessions (disabling telemetry pop-ups, graphical clutter, and heavy background language server bloat).

Before provisioning remote compute, verify local CLI utilities from an elevated or standard PowerShell prompt:
1. Verify GitHub CLI Version:
◦ Command: gh --version
◦ Target: Version 2.45.0 or higher.
2. Verify Authentication & Scopes:
◦ Command: gh auth status
◦ Requirement: Active authentication token with codespace, repo, and read:org scopes.
3. Verify Windows OpenSSH Client:
◦ Command: ssh -V
◦ Requirement: Native Windows OpenSSH enabled in Windows Optional Features to support SSH tunneling via gh cs ssh.

4. Phase 2: Headless Devcontainer Engineering
Standard default devcontainers often attempt to install heavy visual extensions and graphical notifications that produce phantom outputs for screen readers. The devcontainer must prioritize lightweight, deterministic terminal interaction.
4.1 Specification Metrics for .devcontainer/devcontainer.json
• Base Image: [mcr.microsoft.com/devcontainers/base:debian](https://mcr.microsoft.com/devcontainers/base:debian) (lightweight, minimal latency).
• SSH Server Feature: Explicitly inject ghcr.io/devcontainers/features/sshd:1 to guarantee native SSH access without web client dependencies.
• Tool Features:
◦ ghcr.io/devcontainers/features/python:1 (configured for Python 3.12 or 3.14).
◦ ghcr.io/devcontainers/features/rust:1 (optional for multi-language examples).
• Settings Overrides:
◦ Disable terminal bells that cause screen reader stutter.
◦ Set shell prompt to standard, plain non-Unicode characters (avoid Powerline or Nerd Font glyphs that screen readers announce as "private use area character").
5. Phase 3: Screen Reader Curriculum Structure (TUTORIAL.md)
The tutorial documentation must strictly adhere to WCAG 2.1 Level AA documentation standards: no ambiguous links, strict single-H1 hierarchy, linear heading progression (H1 -> H2 -> H3), and no unannounced visual formatting.
5.1 Curriculum Modules Overview
1. Module 1: Authentication and Quota Verification:
◦ Checking available monthly core-hours and gigabyte-month storage allotments.
◦ Command: gh api user/codespaces/secrets or billing overview via CLI.
2. Module 2: Codespace Creation via CLI:
◦ Creating instances with explicit, non-interactive parameters to bypass interactive arrow-key selection prompts (which can be disorienting in NVDA browse mode):
gh cs create --repo <username>/accessible-codespaces-cli --branch main --machine standardLinux32gb --idle-timeout 15m
3. Module 3: Listing and Querying Active Instances:
◦ Extracting raw tabular data versus JSON output for programmatic reading:
gh cs list
gh cs view --json name,state,machineDisplayName
4. Module 4: Terminal-First Connection (The Core Workflow):
◦ Connecting via OpenSSH:
gh cs ssh -c <codespace-name>
◦ NVDA Terminal Configuration: Switching NVDA focus mode (NVDA+Space), using line-by-line review (Numpad 7, 8, 9), and executing standard Linux navigation commands (ls -la, pwd, top).
5. Module 5: File Operations and Synchronization:
◦ Copying files directly without a GUI editor:
gh cs cp README.md remote:/workspaces/accessible-codespaces-cli/
6. Module 6: Port Forwarding for Accessible Web Testing:
◦ Forwarding a cloud application port (e.g., a FastAPI or Flask endpoint) directly to localhost:8000:
gh cs ports forward 8000:8000 -c <codespace-name>
7. Module 7: Lifecycle Management (Storage and Cost Hygiene):
◦ Stopping a codespace: gh cs stop -c <codespace-name>
◦ Deleting a codespace to purge attached storage disks: gh cs delete -c <codespace-name> --confirm
6. Phase 4: Screen Reader Verification and Testing Protocol
A rigorous validation protocol must be completed prior to publishing the sample codebase.
6.1 Screen Reader Testing Metrics
1. NVDA (NonVisual Desktop Access):
◦ Speech synthesizer: Windows OneCore or eSpeak NG.
◦ Review mode: Object review and screen review behavior inside Windows Terminal.
◦ Test criteria: Are terminal escape sequences properly handled, or does the synthesizer read raw ANSI escape codes (e.g., \x1b[32m)?
2. JAWS (Job Access With Speech):
◦ Terminal mode: Virtual PC cursor behavior when switching between prompt input and console output.
3. Interactive Menu Failure Test:
◦ Validate that all tutorial instructions provide explicit flags (e.g., -c <codespace-name>) so screen reader users are not forced to navigate graphical ncurses-style arrow selection menus inside the CLI unless desired.

8. Skeptical Considerations and Edge-Case Mitigations
1. Auto-Generated Codespace Names: GitHub assigns random names like automatic-space-couscous-x7r5. In speech output, these strings can be difficult to parse.
◦ Mitigation: Document the --display-name flag during creation so users can assign predictable names like cs-math-01.
2. SSH Key Pair Prompts: Running gh cs ssh for the first time generates an automated key pair in ~/.ssh. If Windows permissions block key writing, the command fails silently.
◦ Mitigation: Include a pre-flight troubleshooting step in Module 1 to verify Windows .ssh directory permissions.
3. Storage Quota Consumption: Even when stopped, each codespace occupies disk space on your GitHub account.
◦ Mitigation: Emphasize the deletion command (gh cs delete) over the stop command (gh cs stop) for short tutorial workflows.
